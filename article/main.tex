\begin{abstract}
OCI containers share the host kernel, but practical confinement still depends on hand-written seccomp, AppArmor, and capability policies. This paper presents a security-oriented fork of \texttt{runc} that generates such policies inside the runtime. A normal \texttt{runc run --security-scan} invocation relaxes confinement only in memory, traces syscall and capability use with eBPF-based tools, learns AppArmor rules in complain mode, and writes a workload-specific profile set back to the OCI bundle. Later runs enforce those artefacts without carrying helper scripts in the bundle.

Evaluation combines an application-level command-injection laboratory, a kernel-boundary attack corpus, and a performance harness. Scan-then-enforce blocks the Flask laboratory attacks that succeed under stock \texttt{runc}. On a 22-reproducer corpus, the enforced configuration blocks all 17 applicable attack reproducers while allowing the positive control, including all 15 syscall, capability, filesystem, and lateral-movement probes; Docker-default upstream \texttt{runc} blocks 11/20 attempted cells and gVisor blocks 12/20. Performance measurements over 50 recorded repetitions show below 1\% median overhead on CPU, memory, and loopback-network workloads, and about 5.5\% on Redis, while gVisor is 30--73\% slower than Docker on memory, network, and Redis.
\keywords{OCI runtime \and runc \and seccomp \and AppArmor \and Linux capabilities \and eBPF.}
\end{abstract}

\section{Introduction}

Containers are lightweight because they share a kernel, but that design also makes kernel-facing attack surface central to isolation~\cite{wang2022,flauzac2020}. The OCI reference runtime, \texttt{runc}, is fast and widely deployed, yet strong confinement usually requires operators to supply correct seccomp, AppArmor, and capability profiles. Manual policy authoring is specialised work, and cluster-side recorders such as the Security Profiles Operator or Inspektor Gadget assume Kubernetes infrastructure and profile-management workflows~\cite{spo2025,inspektorgadget2025}.

This paper asks whether the runtime can lower that operational cost. We implement a fork of \texttt{runc} that treats profile generation as a runtime-side learning phase. The contribution is threefold: (i) a single-flag workflow for generating syscall, capability, and AppArmor evidence; (ii) finalisation logic that rebuilds privileges from observed behaviour rather than merging with broad defaults; and (iii) self-contained scanner hooks implemented as hidden runtime sub-commands, preserving OCI bundle portability.

\section{Runtime Design}\label{sec:implementation}

The implementation extends \texttt{runc run} with an optional scanning branch. Without \texttt{--security-scan}, the bundle runs through the ordinary OCI path. With the flag, the runtime relaxes confinement in memory, installs tracing hooks, runs the container, stops tracers, and finalises generated profiles under the bundle's \texttt{generated/} directory. The on-disk \texttt{config.json} is not widened before the scan.

Capability finalisation normalises names to OCI \texttt{CAP\_*} spelling and replaces all capability buckets from an empty set extended only with observed capabilities. This invariant prevents repeated scans from preserving privileges merely because they appeared in earlier configurations. AppArmor and seccomp are similarly evidence-based: the runtime records the exercised paths and syscalls, then embeds the resulting deny-by-default policies for subsequent runs.

\section{Evaluation}\label{sec:evaluation}

All quantitative campaigns ran on \texttt{perf-bench}, an Ubuntu~24.04.4 VirtualBox guest with kernel~6.8.0-124, cgroup~v2, four vCPUs (AMD Ryzen~7~7700), and AppArmor enabled for the security corpus. The VM lacks KVM and CPU-governor pinning; we therefore report medians and treat small differences as measurement noise.

\subsection{Application Security Laboratory}\label{sec:eval-security}

The \texttt{runc-hardened-test} laboratory~\cite{runchardenedtest} packages a deliberately vulnerable Flask system-monitor application. A scan driven by legitimate UI, ping, and calendar-upload traffic produced a deny-by-default seccomp profile, an AppArmor profile, and a capability trace. After enforcement, the same command-injection payloads that succeeded under stock \texttt{runc} were blocked: the learned seccomp profile denied process-creation syscalls on the attack path, while AppArmor preserved legitimate application storage paths. A controlled ablation that re-enabled \texttt{execve} restored a shell, but most follow-on reads, mount probes, and persistence attempts remained blocked by the remaining layers.

\subsection{Kernel-Boundary Attack Corpus}\label{sec:eval-security-corpus}

The \texttt{security-evaluation} harness~\cite{securityeval} replays 22 shell-based reproducers across four configurations: C0 (Docker-default upstream \texttt{runc}), C1 (hardened \texttt{dpttk/runc} with a raw bundle), C2 (the same runtime with generated profiles enforced), and C3 (gVisor \texttt{runsc}). C0 is the weak security baseline. C3 is a sandbox reference, not the same mechanism as workload-specific profile enforcement.

An attack is blocked when it fails with policy or permission evidence, kernel audit denial, or absence of the expected side effect. Campaign \texttt{20260618-222423} stores stdout/stderr and audit-window logs for every attempted cell under \texttt{results/latest/logs}. Table~\ref{tab:security-effectiveness} summarises the aggregate results.

C2 blocks all 15 syscall, capability, filesystem, and lateral-movement probes, compared with 9/15 for C0 and 10/15 for C3. The positive control succeeds in all configurations. \subsection{Performance Harness}\label{sec:eval-performance}

The \texttt{performance-evaluation} harness~\cite{perfeval} separates profile preparation from measurement. \texttt{stock} and \texttt{proposed} use the same hardened binary and OCI-bundle launcher; \texttt{stock} uses raw bundles, while \texttt{proposed} enforces generated seccomp, AppArmor, and capability profiles. Docker and gVisor are measured through Docker. This differs from C0 in the security corpus, where C0 means Docker-default upstream \texttt{runc}.

Campaign \texttt{20260616-193735} ran 10 warm-up and 50 recorded repetitions for sysbench CPU/memory, loopback iperf3, and Redis SET/GET. Throughput overhead is positive when the subject is slower than its baseline.

\section{Discussion}\label{sec:analysis}

Runtime-side profiling is a middle ground between default \texttt{runc} and full sandboxing. It does not replace gVisor's kernel-surface reduction, but it narrows a shared-kernel runtime with low measured overhead and without requiring a cluster recorder. Its main safety invariant is replace-from-evidence: finalisation does not union observed privileges with historical broad defaults.

The approach has clear limits. Dynamic profiles cover only exercised behaviour; rare paths need representative tests. UID~0 workloads can under-report capability checks. File capabilities embedded in executable xattrs, such as the raw-network privilege on \texttt{ping}, are not yet merged automatically. Finally, deployment mistakes such as \texttt{--privileged} containers or host namespace sharing bypass what bundle-level scan output can repair.

\section{Related Work}\label{sec:related}

Prior work compares native \texttt{runc}, gVisor, and Kata in terms of performance and isolation~\cite{wang2022,viktorsson2020,volpert2024}, but rarely evaluates \texttt{runc} with workload-specific generated policies. Lopes et al.~\cite{lopes2020} automate seccomp profile generation; Mattetti and Allouche~\cite{mattetti2020} argue for layered Linux hardening. Cluster-side recorders such as the Security Profiles Operator, Inspektor Gadget, and Tetragon target Kubernetes environments~\cite{spo2025,inspektorgadget2025,tetragon2025}. Our work moves the same evidence-collection idea into the OCI runtime layer.

\section{Conclusion}\label{sec:conclusion}

This paper presented a \texttt{runc} fork that generates and enforces workload-specific seccomp, AppArmor, and capability profiles. The runtime blocks command-injection exploitation in an application laboratory and blocks all 15 kernel-boundary probes in a reproducible attack corpus, while Docker-default upstream \texttt{runc} and gVisor allow several filesystem, lateral-movement, or misconfiguration cases in the same matrix. Enforcement adds near-zero overhead on CPU, memory, and loopback-network workloads and about 5.5\% on Redis, well below gVisor's sandbox overhead on the same host. Within its stated limits, runtime-side profiling offers a practical way to raise the security floor for plain OCI deployments.
