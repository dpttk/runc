
\chapter{Experiments}\label{ch:experiments}

This chapter reports the experimental evaluation of the proposed runtime. It instantiates the methodology of Section~\ref{sec:design-eval} on the \texttt{runc-hardened-test} security laboratory (empirical) and on the competitive landscape from Chapter~\ref{ch:litreview} (analytical). Section~\ref{sec:exp-setup} describes the setup; Section~\ref{sec:exp-results} presents the outcomes.

\section{Experimental Setup}\label{sec:exp-setup}

\textbf{Host and binaries.} The security laboratory runs on Ubuntu~24.04 with cgroup~v2 and AppArmor enabled. It builds two runtime binaries---upstream \texttt{runc-stock} and the proposed \texttt{runc-hardened}---and packages a single OCI bundle with an intentionally vulnerable Flask workload (system monitor plus calendar). Command injection in \texttt{/diag/ping} and \texttt{/diag/dns} is retained on purpose: the experiment does not measure whether remote code execution is possible, but what an attacker can do \emph{after} reaching shell execution inside the container.

\textbf{Protocol.} The reproducible workflow is:
\begin{enumerate}
    \item \texttt{sudo ./scripts/setup.sh} --- build binaries and prepare the bundle;
    \item \texttt{sudo ./scripts/run-apparmor-public.sh --baseline} --- run under stock \texttt{runc} without generated profiles;
    \item replay a fixed set of post-exploitation payloads through the injection endpoint and record baseline behaviour;
    \item \texttt{sudo ./scripts/scan.sh} --- run \texttt{runc-hardened --security-scan} while exercising only legitimate HTTP paths (UI, logs, ping, DNS, calendar upload);
    \item \texttt{sudo ./scripts/apply.sh} --- pin generated AppArmor, seccomp, and capability artefacts;
    \item \texttt{sudo ./scripts/run-apparmor-public.sh --hardened} --- enforcement run;
    \item replay the same payloads and compare blocked behaviour, audit logs, and profiles.
\end{enumerate}
Reproducer scripts and evidence collection steps are documented in the laboratory \texttt{README.md}. The host requires root for \texttt{runc}, AppArmor profile loading, and BPF tracing.

\section{Experimental Results}\label{sec:exp-results}

\subsection{Scope and threat model}

The laboratory answers RQ1 (profile quality) and RQ3 (containment vs.\ stock \texttt{runc}) on one representative workload. The attacker model is application-layer command injection followed by arbitrary shell commands in the container context. Kernel-side escape primitives (runtime CVEs, mounted \texttt{docker.sock}, privileged containers) are out of scope, consistent with Section~\ref{sec:design-threat}.

\subsection{Profile generation (RQ1)}

A single \texttt{runc run --security-scan} pass, followed by scripted legitimate traffic, produced the expected artefacts under \texttt{oci-bundle/generated/}: \texttt{seccomp.json} with \texttt{defaultAction=SCMP\_ACT\_ERRNO}, an AppArmor profile learned in complain mode, and \texttt{capable-bpfcc.log} from the cgroup-wide BPF trace. Finalisation embedded the seccomp allow-list and narrowed \texttt{process.capabilities} in \texttt{config.json} without widening privileges relative to the trace.

Table~\ref{tab:profquality-lab} summarises the artefact families. Three profile-quality findings affect how operators should read the output:

\begin{itemize}
    \item \textbf{Seccomp.} The allow-list covered syscalls exercised by the Flask process, subprocess invocations (\texttt{ping}, \texttt{nslookup}), and file I/O on application paths.
    \item \textbf{AppArmor.} Initial enforcement missed writable paths such as \texttt{/var/lib/sysmon-cal} because the audit collector matched only \texttt{apparmor=DENIED}, while complain mode logs would-be denials as \texttt{apparmor=ALLOWED}. The runtime collector was updated to accept both forms; unit tests now cover calendar upload writes.
    \item \textbf{Capabilities.} The \texttt{capable-bpfcc} trace did not record \texttt{CAP\_NET\_RAW} required by \texttt{/usr/bin/ping} when the capability is carried as a \emph{file capability} (\texttt{security.capability} xattr) rather than through \texttt{cap\_capable} events. Until the runtime merges file capabilities from executed binaries, the laboratory documents an explicit post-scan adjustment (\texttt{REQUIRED\_CAPS=CAP\_NET\_RAW}) in \texttt{apply.sh}.
\end{itemize}

\subsection{Containment effectiveness (RQ3)}

The vulnerable HTTP endpoints remained exploitable by design; the difference appears in post-exploitation actions. Baseline execution left an effective in-container root context after injection. Hardened execution blocked reconnaissance commands as well: the injected \texttt{sh -c} chain could not spawn \texttt{bash} or fork helpers because the enforced seccomp allow-list excludes process-creation syscalls absent from the scan trace. Sensitive-file reads, reverse-shell setup, and mount-based probing were blocked for the same reason. Intended application behaviour was preserved once the documented capability and writable-path adjustments in \texttt{apply.sh} were applied.

\subsection{Edge cases and drawbacks}

The laboratory run surfaced limitations that are part of the evaluation, not one-off implementation anecdotes:

\begin{itemize}
    \item \textbf{Scan coverage.} Profiles reflect only paths exercised during the scan window; cron jobs, error handlers, and certificate rotation are absent unless driven explicitly.
    \item \textbf{File capabilities.} \texttt{ping} illustrates privileges embedded in binaries rather than observed through \texttt{cap\_capable}; operators must merge these manually until the scanner does.
    \item \textbf{AppArmor complain mode.} Learning depends on complete audit parsing; mixed \texttt{ALLOWED}/\texttt{DENIED} records must both be collected.
    \item \textbf{Enforcement is not scan-only.} \texttt{apply.sh} workarounds (\texttt{REQUIRED\_CAPS}, \texttt{WRITABLE\_PATHS}) mean the hardened run documents honest operator steps rather than claiming fully automatic enforcement without review.
\end{itemize}

\begin{itemize}
    \item \textbf{Manual tuning} can match or exceed profile tightness but scales poorly across services and releases; the runtime scanner automates the same three mechanisms for teams without MAC expertise.
    \item \textbf{Cluster recorders} (SPO, Inspektor Gadget) target the same profile shapes with broader multi-workload coverage and release diffing, at the cost of Kubernetes and platform engineering.
    \item \textbf{Sandboxed runtimes} (gVisor, Kata) provide stronger kernel isolation on published benchmarks~\cite{wang2022,viktorsson2020,volpert2024} but do not emit reusable OCI profiles and impose permanent runtime overhead; they are compared here only through the literature, not through measurements in this thesis.
\end{itemize}

Performance comparison between stock \texttt{runc}, hardened enforcement, and sandboxes is deferred to future work (Chapter~\ref{ch:conclusion}).
